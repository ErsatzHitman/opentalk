## FLAC upload experiment (PLAN 9.5, Phase 8)

**Decision: not adopted; uploads stay 16 kHz mono PCM WAV.** The bar was "saves at least 30 ms on a median connection".

Method: a throwaway program (not part of the repo) encodes the fixture clips with `flacenc` 0.5.1 (pure Rust, `default-features = false`, default config, fixed 4096-sample blocks, release build with fat LTO) and times 21 encodes per clip. The clean clip's FLAC was decoded with ffmpeg and is bit-exact with the source WAV. Upload time was measured on a paced 127.0.0.1 TCP transfer (1460-byte writes, deadline-paced to the simulated uplink, wall time until the receiver has all bytes and replies; median of 5). Two inputs bracket real audio: the TTS fixture as is (the best case for FLAC, digital silence between words) and the same clip with +-30 LSB uniform noise added (about -60 dBFS, a typical quiet-room mic floor; real mics are often noisier, which compresses worse).

| Clip (16 kHz mono) | WAV bytes | FLAC bytes | FLAC / WAV | Encode median / p95 (ms) |
|---|---|---|---|---|
| tts_clean.wav, 6.03 s | 193,004 | 83,207 | 0.431 | 9.6 / 12.1 |
| tts_fillers.wav, 8.47 s | 271,244 | 128,297 | 0.473 | 14.9 / 32.7 |
| tts_clean.wav + noise 30 | 193,004 | 109,206 | 0.566 | 11.2 / 24.3 |
| tts_fillers.wav + noise 30 | 271,244 | 158,109 | 0.583 | 16.5 / 29.1 |
| tts_fillers.wav + noise 100 (about -50 dBFS) | 271,244 | 171,025 | 0.631 | 15.7 / 36.4 |

Measured paced upload of the 8.47 s clip (milliseconds, WAV vs FLAC, before encode time):

| Uplink | Clean: WAV / FLAC / saved | Noise 30: WAV / FLAC / saved |
|---|---|---|
| 2 Mbps | 1087 / 585 / 502 | 1086 / 665 / 421 |
| 5 Mbps | 437 / 211 / 226 | 436 / 257 / 179 |
| 10 Mbps | 217 / 103 / 114 | 220 / 130 / 90 |

The 20 and 50 Mbps rows of the paced test were not usable: Windows timer granularity (about 1 ms sleeps against 0.5 ms packet intervals) made the runs bounce (for example 362 ms against an expected 108 ms), so those rows come from the arithmetic that the 2/5/10 Mbps measurements confirm to within 1%: `bytes * 8 / rate`.

Net saving (upload time saved minus encode time, ms; encode cost taken as 1.76 ms per audio second clean, 1.94 noisy). Format: saved before encode / net after encode.

| Dictation, content | 2 Mbps | 5 Mbps | 10 Mbps | 20 Mbps | 50 Mbps |
|---|---|---|---|---|---|
| 5 s, clean | 337 / 328 | 135 / 126 | 67 / 59 | 34 / 25 | 13 / 5 |
| 5 s, mic noise | 267 / 257 | 107 / 97 | 53 / 44 | 27 / 17 | 11 / 1 |
| 8.5 s, clean | 571 / 556 | 229 / 214 | 114 / 99 | 57 / 42 | 23 / 8 |
| 8.5 s, mic noise | 452 / 436 | 181 / 164 | 90 / 74 | 45 / 29 | 18 / 2 |

Reading:

- FLAC clears 30 ms net only on slow uplinks: below roughly 13 Mbps for a 5 s dictation and below roughly 20 Mbps for an 8.5 s one (noisy input; 17 Mbps for 5 s clean). On a 20-50 Mbps uplink, which is a conservative stand-in for a median fixed connection (mobile is lower, broadband usually higher), a typical 5-8.5 s dictation nets 1-42 ms, and only the clean (best-case) 8.5 s clip at 20 Mbps clears 30 ms; every mic-noise case is under the bar.
- The model ignores TCP slow start and TLS record overhead. With a pre-warmed keep-alive socket (PLAN 9.3) the 130-270 KB body spans several round trips either way, so the real saving at high bandwidth is bounded by the bandwidth term above plus at most about one RTT, and no measurement here supports counting on that.
- Cost: `flacenc` adds 248,320 bytes to a release binary (526,336 against 278,016 bytes for the same program without it), about 242 KB. That is 3.2% of the 7,877,632-byte (7.51 MiB) executable of that build and more than twice the 122,368 bytes left under the 8,000,000-byte budget (PLAN section 1: MB is decimal), so it would not even have fit, for no win at the target connection speed.
- Compatibility risk the WAV path does not have: every provider needs a verified FLAC accept path (content type, file name, extension sniffing; Gemini inline data and the Realtime/streaming providers differ), and each would need a WAV fallback on rejection.
- The encode is also on the stop-to-text path (about 15 ms for 8.5 s) unless it is moved into the recording thread, which spends CPU while the 1.5% recording target is tight on small laptops (see the 4-core projection above).

Revisit only as an opt-in for slow uplinks (for example when a measured upload rate stays below about 10 Mbps), not as the default format. Until then the PLAN section 1 upload row stays "silence-trimmed 16 kHz mono PCM WAV", logged in bytes per request (249,964 bytes in the benchmark above).

## Method

- Release build, GNU toolchain, `opt-level = 3`, fat LTO, stripped. One executable; Settings is the same exe started as `--settings`.
- Each scenario starts a fresh daemon with its own `OPENTALK_HOME`. Dictations are driven through the same message the hotkey
  produces (`--bench toggle` / `--bench dictate`); the microphone is replaced by `OPENTALK_INJECT_WAV` (real-time playback of
  `tests/fixtures/tts_fillers.wav`, 8475 ms) except where stated.
- STT goes to `opentalk --bench mock-stt`, an in-repo OpenAI-shaped server on 127.0.0.1 that answers instantly, so network
  speed does not enter the numbers.
- Samples are taken every 250 ms with `Process.TotalProcessorTime`, `WorkingSet64` and `PrivateMemorySize64`.
- Latencies come from the daemon's own QPC-stamped log lines (`latency seq=...`), read back with `--bench latency`.
- Per-thread CPU uses `ProcessThread.TotalProcessorTime` and the thread names Rust sets (`SetThreadDescription`).

## Notes

- **opengl32.dll is delay-loaded** (`build.rs`). Only the Settings window draws with OpenGL, but a load-time import put
  `opengl32.dll` into the daemon too, and overlay injectors that hook GL processes (RivaTuner/MSI Afterburner, which runs on
  this machine) then treated the daemon as a 3D app: its private commit jumped from ~2 MB to ~58 MB at the first STA
  `CoInitializeEx`. With the delay-load import the daemon never loads the DLL; Settings loads it on its first WGL call.
  The Settings process's large private-bytes figure is that same injector inside a real GL process; its working set is small.
- **Settings private bytes**: the PLAN section 1 Settings figure (80 MB) is read as working set, not as `PrivateMemorySize64`.
  The Settings process commits ~265 MB, almost all of it the OpenGL driver's command and shader pools reserved at context
  creation (plus any overlay hook such as `RTSSHooks64.dll`); it is mostly untouched, so it never enters the working set.
  `ui/app.rs::native_options` already asks for no depth, stencil or MSAA (eframe's defaults), and vsync or
  `hardware_acceleration` do not change it; software GL is 1.1, which `egui_glow` rejects. Only a non-GL renderer would
  avoid it. Documented deviation; the daemon never loads `opengl32.dll` and does not pay it.
- **Recording CPU is the pill, kept to the lane**: once the entrance has settled the pill caches its static layer (shadow,
  body, logo) and each frame redraws only the 52x24 waveform lane, uploads only that rectangle and presents it with
  `UpdateLayeredWindowIndirect` (`prcDirty`). A frame whose bars all moved by <= 1/255 px is skipped, which is every
  frame while the input is silent. The thinking glow keeps its 60 fps but also caches the chrome. WASAPI capture and the
  VAD/level meter stay well under 1% of one core. The row "Main thread while recording" is the figure the pill is judged by
  (<= 6% of one core is <= 1.5% on a 4-core laptop).
- **Working set and the app bubble**: the active-app icon of a classic Win32 executable comes from `PrivateExtractIconsW`
  (user32 only), then `SHGetFileInfoW` (in its own COM apartment). `IShellItemImageFactory` is the last resort, used
  only for packaged (UWP / MSIX) apps or when both lighter paths return nothing, because it loads ~35 shell DLLs (XAML,
  StateRepository, thumbcache, ...) into the daemon for the rest of its life (~+17 MB working set of shared image pages,
  ~2-4 MB private). Since commits d53ba4d and 7fbcd92 those shell DLLs stay out of the daemon for Win32 apps. The
  bubble-on working set on an unlocked desktop with a real foreground app has not been re-measured since the change and is
  still to be done: the "app bubble on" rows of this report use whichever window was in front of the benchmark, and the
  earlier unlocked-desktop section predates it.
- Clipboard and paste timings in this run are not representative: the workstation was locked (LogonUI active), where Windows refuses clipboard access, so `copy_to_clipboard` exhausts its retries (~95 ms) and real-paste e2e runs are skipped. Re-run on an unlocked desktop.
